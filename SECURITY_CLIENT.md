# Sécurité du client local

Le processus `temba` tourne sur le poste utilisateur. Il reçoit des définitions non secrètes du catalogue et contacte directement les MCP. Le catalogue, l’agent LLM et les résultats des outils ne reçoivent ni access token, ni refresh token, ni clé permettant de récupérer une session distante.

Chaque catalogue a son espace d’identifiants, sa session OAuth, son ETag et ses credentials. Un identifiant `catalogue.mcp.tool` est routé vers ce catalogue uniquement ; une révocation ferme ses connexions protégées sans retirer celles des autres catalogues. Les tables privées sont indexées par catalogue puis par MCP et restent liées à l’endpoint attendu. Les connexions navigateur partageant un port de callback sont mises en attente pour éviter les collisions. Le catalogue local est chargé automatiquement par chaque processus Temba. Sa passerelle interne utilise exclusivement un port loopback alloué automatiquement ; elle ne publie ni commandes ni variables privées et ne fournit aucune API de modification.

Les sessions OAuth vivent uniquement dans des objets du processus local. Aucun token, code d’autorisation ou vérificateur PKCE n’est écrit dans un fichier ou un trousseau. Le binaire natif se lance directement. Pour l’installation optionnelle via uv, son cache contient le binaire distribué, pas les credentials. Une relance du client nécessite une nouvelle authentification.

La commande `temba catalog` utilise une session distincte en mémoire pour lire les définitions autorisées. Elle ne récupère pas le token d’un processus MCP déjà lancé et ne contacte pas les MCP distants. Elle n’affiche ni les tokens OAuth ni les valeurs privées du YAML. Le flag `--json` réserve stdout au JSON ; les instructions de connexion vont sur stderr. Les textes du catalogue sont échappés pour éviter les séquences de contrôle dans l’affichage terminal.

Le flux OAuth utilise Authorization Code avec PKCE S256, un état aléatoire, un callback loopback et un délai de dix minutes. Le listener est créé avant l’ouverture du navigateur. L’état est vérifié avant consommation du callback ; un callback incorrect ne termine pas le flux attendu. Un callback correct est consommé une seule fois. Un issuer présent dans le callback doit correspondre à celui de la découverte ; il est obligatoire lorsque le fournisseur annonce le support de ce paramètre. La découverte exige un issuer cohérent. Sans liste `oauth.allowedOrigins` non vide, Temba fait confiance au fournisseur annoncé par le MCP, avec des destinations supplémentaires sur des adresses publiques uniquement. HTTPS est obligatoire par défaut ; `allow_insecure_http` autorise HTTP pour les destinations locales et distantes, sans désactiver la validation des certificats HTTPS ni le contrôle des destinations OAuth. Les IP privées, loopback, link-local et réservées sont refusées ; la résolution DNS utilisée pour chaque nouvelle connexion applique aussi ce contrôle, y compris pour le renouvellement des tokens. Le navigateur reçoit une URL d’autorisation validée, mais ses propres redirections et résolutions DNS restent sous son contrôle. L’origine exacte du MCP configuré reste autorisée, y compris pour les tests locaux. Une liste non vide conserve le mode restrictif : seules les origines déclarées et celle du MCP sont autorisées. Elle permet notamment de déclarer explicitement un fournisseur interne.

Chaque session dispose de son propre verrou de refresh. Le refresh token tournant remplace l’ancien ; l’absence d’un nouveau refresh token conserve le précédent. Un rejet `invalid_grant` supprime les credentials. La marge de renouvellement vaut le minimum de 60 secondes et 10 % de la durée de vie du token. Le transport récupère le token courant pour chaque requête, y compris la reprise d’un stream, sans conserver un ancien bearer dans sa configuration.

Le transport vérifie la destination exacte avant de joindre un token OAuth. TLS 1.3 reste activé, avec des groupes ECDHE classiques (X25519, P-256, P-384) pour éviter les resets constatés sur certains endpoints Atlassian avec les groupes hybrides ML-KEM. La validation des certificats reste active. Les clients HTTP ne suivent pas les redirections et n’utilisent pas implicitement les variables de proxy. Les valeurs privées des headers proviennent de valeurs directes dans `catalogs[].tools.<id>.headers` ou de références explicites dans `headersFromEnv`, avec une destination exacte approuvée localement. Une chaîne est toujours littérale ; une valeur directe est enregistrée sur disque dans le YAML, qui doit rester privé. Les secrets OAuth restent uniquement en RAM. Le buffer du YAML et les valeurs directes détenus par le client utilisent Zeroizing ; les erreurs de parsing ne recopient pas le contenu du fichier dans les logs. OAuth et plusieurs headers X-* peuvent coexister ; le catalogue ne peut pas remplacer Authorization lorsqu’OAuth est actif. Les headers supplémentaires ne sont envoyés qu’au MCP exact, y compris sa sonde de découverte, jamais aux endpoints OAuth ou de métadonnées. Le catalogue ne peut pas choisir cette variable ou modifier l’association. Il peut déclarer des valeurs publiques non secrètes ; celles-ci sont lisibles par ses utilisateurs et ne nécessitent pas de configuration locale. Les headers privés optionnels manquants sont omis ; les headers mandatory manquants bloquent avant toute requête réseau. Aucun préfixe n’est ajouté aux valeurs privées.

Les appels métier ont un timeout et ne sont pas rejoués automatiquement : après un timeout, le serveur peut avoir exécuté l’opération. L’utilisateur doit vérifier son résultat avant de relancer une écriture.

La suppression d’un serveur, son changement de configuration, une déconnexion ou la fin du processus ferme les connexions concernées. Les buffers possédés par le client pour les secrets utilisent `Zeroizing`; les core dumps sont désactivés sur Unix. **Cela ne garantit pas l’effacement de toutes les copies** : parsing JSON, bibliothèques HTTP, TLS, allocations temporaires et variables d’environnement peuvent en conserver. Rust n’est pas une garantie d’effacement intégral de la RAM.

Le poste reste dans le périmètre de confiance. Un programme capable de lire la mémoire du client ou de s’exécuter sous le compte utilisateur peut exploiter ses credentials. La RAM peut également être paginée ; la protection du swap relève de l’OS. Un token statique fourni par variable d’environnement a la durée de vie de cet environnement, indépendamment de la déconnexion MCP.

Les définitions et les outils distants sont des données non fiables. Le filtre `labels` est une préférence locale, pas une ACL. Le catalogue filtre les entrées selon les groupes du token Keycloak vérifié ; le client ferme les connexions retirées après rafraîchissement et supprime toutes les entrées non publiques lors de la perte de connexion au catalogue authentifié. Ces règles protègent la visibilité du catalogue, pas l’accès direct à un MCP connu ni les permissions propres aux services distants. Dans le catalogue central, les destinations MCP et les éventuelles restrictions d’origines OAuth sont définies par l’administrateur. Avec `dynamic_catalog.enabled`, le LLM peut déclarer ses propres connexions éphémères, sous les mêmes validations HTTPS et de découverte OAuth.

Les logs utilisent stderr et indiquent les noms et états des connexions. Aucun subscriber de tracing SDK n’est installé, pour éviter les dumps de requêtes et de secrets. Ne pas partager un dump mémoire ou un environnement contenant des tokens.


Le catalogue local éphémère n'utilise aucune identité spécifique au client LLM. Chaque ajout a une clé aléatoire de 256 bits, conservée dans l'ID. Les recherches globales n'exposent ni ces clés ni les entrées ; recherche et appel nécessitent de présenter la clé. Les noms peuvent être identiques sans partager de connexion. La possession de la clé autorise l'utilisation : ce n'est pas une authentification de conversation. Les diagnostics affichent un nom lisible plutôt que la clé.

Les valeurs privées d'un ajout sont indépendantes du YAML et des autres ajouts ; elles ne peuvent pas être récupérées via la recherche. Elles ne sont envoyées qu'au endpoint déclaré à la création, qui ne peut pas être modifié avec cet ID. OAuth reste une action navigateur distincte. La déconnexion explicite et l’arrêt du processus retirent l'ID, ferment le transport et effacent les buffers privés possédés ; le processus ne reçoit pas de notification universelle de fin de conversation. L'historique éventuel des arguments et réponses est géré par le client LLM, pas par Temba.


## MCPs stdio hébergés localement

Seul le fichier `local_catalog.servers` peut définir un exécutable (`command`) et ses arguments séparés (`args`). Temba les lance automatiquement sans évaluation shell et impose une écoute loopback lorsque des entrées stdio sont présentes. Les catalogues centraux et l'ajout dynamique restent limités aux définitions HTTP. Le catalogue REST ne publie jamais les commandes, arguments, répertoires ou variables d'environnement ; il annonce uniquement les métadonnées MCP et les endpoints HTTP générés. Les endpoints MCP vérifient Host et rejettent les en-têtes Origin des navigateurs. Les résultats des tools restent sous le contrôle du MCP exécuté.

Un processus est partagé par les connexions à une même entrée ; les différentes entrées ont des processus distincts. L'environnement hérité est réduit aux paramètres usuels d'exécution ; les autres valeurs sont déclarées explicitement via `env` ou `envFromEnv`. Un timeout arrête le processus sans rejouer le call. L'arrêt normal de Temba (fin de session MCP, Ctrl+C ou SIGTERM Unix) ferme les connexions et termine les groupes de processus ou jobs Windows associés. Aucun mécanisme ne transforme ces programmes en sandbox : ils possèdent les droits du compte qui lance Temba. Chaque instance utilise une passerelle interne sur un port loopback libre.

Les diagnostics de configuration indiquent le fichier, la position YAML et le chemin du champ. Ils ne reproduisent ni les valeurs rejetées ni les extraits YAML du parseur. Les erreurs de processus nomment les références de variables manquantes sans afficher leurs valeurs ; les erreurs HTTP ne relaient ni corps de réponse ni URL contenant des credentials.
